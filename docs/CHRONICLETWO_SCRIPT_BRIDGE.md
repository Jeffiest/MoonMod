# ChronicleTwo-Script compatibility bridge

## What the existing toolchain does

[`fakegenie/DC2-Toolkit`](https://github.com/fakegenie/DC2-Toolkit), previously linked as `fakegenie/ChronicleTwo-Script`, is an offline script and asset authoring toolchain for Dark Chronicle's PAL disc data. It extracts and decompiles scripts, lets a mod target and override named functions (including native calls), allocates stable script numbers such as flags and programs, and rebuilds a patched image. Its asset pipeline also supports authored map scenes, models, textures, sounds, text, and added map scripts. The repository includes examples of a custom animated character and a new map with an entrance and return route.

That workflow is valuable for MoonFactory's creator tools, but it is a separate execution path from a mod running inside the PC port. An ISO patch that compiles correctly does not prove that the PC runtime can load the same map, animation, or model. MoonFactory must report these as build-only or unsupported until its port adapter can load and test the corresponding content.

## Bridge direction

Keep the MoonFactory package manifest and Lua API as the common runtime contract. Add an optional, versioned `chronicle-two-script` package component that can:

1. Import a ChronicleTwo-Script mod's metadata, dependencies/order, target scripts, function fingerprints, `NEW_FLAG`/`NEW_COUNTER`/`NEW_PROGRAM` identifiers, and asset `add`/`replace` declarations.
2. Preserve C script patches and their target fingerprints as a build-time component. `#pragma override`, `original()`, and native wrappers must remain explicit build actions; they are not Lua callbacks or live executable hooks.
3. Convert supported source assets and definitions into MoonFactory-owned package resources with stable namespaced IDs. Keep original C2 asset IDs and source paths in provenance metadata so conflicts and updates can be diagnosed.
4. Emit a capability/build report that distinguishes content loaded by the PC port at runtime from content that only works in a locally rebuilt script image.

The import/export tool must use the user's local extracted data and installed C2 toolchain. MoonFactory packages should contain authored mod files and metadata, not extracted disc scripts or game assets.

## Content mappings to verify

| ChronicleTwo-Script concept | MoonFactory destination | Proof required |
| --- | --- | --- |
| Added Lua function | `scripts.register_function` / `scripts.list_functions` / `scripts.call_function` | Shared runtime proves owner cleanup, callback isolation, and dependency-scoped discovery and calls. |
| Function override or native wrapper | `scripts.override` for the active scene event-program runner; build-time script patch for named function bodies and native wrappers | PC runtime supports the scene event hook with stable ordering, owner cleanup, and one-shot native call-through. Named function patching and C2 native wrappers still require build-time target fingerprints, conflict reporting, and restore after rebuild. |
| `NEW_FLAG`, `NEW_COUNTER`, `NEW_PROGRAM`, and `NEW_MONSTER_VAR` | `world.story_flag_*`, `world.story_value_*`, `scripts`, and a build-time symbol allocation manifest | Stable name-to-number mapping across rebuilds, retained allocations after disabling a mod, and save compatibility; the current runtime APIs take game-native numeric IDs and do not yet allocate C2-Script symbols by name |
| Asset IDs in `replace` / `add` | `resources.override` for an existing native PC file path; typed `models`, `animations`, `audio`, and `localization` APIs where supported | Native data-reader tests verify existing-path replacement and safe fallback; Lua runtime tests verify owner cleanup on unload. Format conversion, type/rig validation, and any `add` asset that has no indexed PC path remain open. |
| Added map scene, script, door, and return route | `locations.register` and `world.transition` | New map identity, native resource load, entrance and exit, save/load identity, and deterministic headless/gameplay entry |
| New character pack with model, rig, skin, and motion | `characters.register` supports data-only enemy variants inheriting native assets; `characters.spawn` routes them through the dungeon manager; `models.resolve` reports native model paths and package override state | Native table resolution, stat overrides, spawn request validation, and no-dungeon failure pass. A successful live spawn needs extracted game data; custom model/rig loading remains open. Animation enhancements and fighting styles are deferred until model-rigging work is in scope; existing embedded-motion playback stays at its verified baseline. |
| Dungeon floor map and generator | `dungeons.register` and `world.register_dungeon` | Reachable floor graph, entry/exit, save/load, and no collision with native floor IDs |

These mappings are targets, not current support claims. `resources.override` can replace an existing PC data-reader path when the package supplies a valid native-format file no larger than the retail file. `models.resolve` reads a model entry already present in the native monster table and reports whether its `.chr` path has a package override registered; it does not validate or load custom models. The bridge does not convert C2-Script assets or create native path/index entries. ChronicleTwo enemy registration covers stat variants that reuse retail behavior; it does not import the C2-Script example's model, rig, skin, or motion. The PC adapter's added-dungeon support appends a room to an existing Chronicle Two dungeon; it does not register the C2-Script example's wholly new town-style map or its script/asset bundle.

## Compatibility verification

- Record the C2-Script repository revision, definition-set version, target disc fingerprint, and MoonFactory package schema/API versions in every conversion report.
- Run C2-Toolkit's own Rust tests, `mod check`, and per-mod `mod test` before accepting imported script patches. Its `build` command checks modified scripts read back from the new image; keep that result separate from PC runtime verification.
- Run MoonFactory's native adapter and executable headless scenarios for every capability the PC port claims to load.
- Keep separate fixtures for script-only hooks and an added map with an entrance and return route. Character fixtures can cover existing data-only variants; defer authored-rig and fighting-style fixtures until model-rigging work is in scope. Compare normalized allocation and conflict reports across repeated clean builds.
- Refuse automatic conversion when a source override, asset format, game fingerprint, or PC loader behavior cannot be mapped safely; retain the source component and report the unsupported item precisely.

Workspace checks: the original ChronicleTwo-Script URL redirects to [DC2-Toolkit](https://github.com/fakegenie/DC2-Toolkit). Its [v0.1.0 Windows release](https://github.com/fakegenie/DC2-Toolkit/releases/tag/v0.1.0) archive was SHA-256 verified, then used with the supplied PAL ISO in an isolated temporary work tree. `dc2tk setup` produced 1,398 script files and 1,097 libraries. The complete retail script verification passed all 1,398 files through format, native, assembly, and source stages; 227 native-call numbers lack registered names. The Calculator example passed static inventory, `dc2tk mod check` with the PAL image, and three `dc2tk mod test` cases. The MoonFactory bridge built a new offline image, recorded the output image hash, and the image's re-extracted scripts passed all four verification stages. The built image's decompiled source retains 45 assembly-block functions. The exact launcher hash and command outputs are in [`c2script-calculator-pal-build-20261016.json`](../artifacts/c2script-calculator-pal-build-20261016.json); the full input-disc and built-image reports are linked from the [roadmap](ROADMAP.md#3-content-pipeline-bridge). These checks validate the offline toolchain only; no patched ISO was launched in PCSX2 or loaded by MoonFactory's PC runtime.

The separate legacy Python CLI checkout still passes 170 tests with one skipped. Its older raw files are under `extracted/` and decompiled C sources under `decompiled/`; its own long all-script round-trip was stopped before producing a report. The converted ChronicleTwo game data also passes a 120-frame retail-data headless title launch.

## Local compatibility report tool

`tools/chronicle_two_script_bridge.py` inventories one mod in a user's local DC2-Toolkit checkout. It reports patch targets, override/native-wrapper and per-frame directives, `original()` calls, requested `NEW_*` names, whole script files, raw disc overrides, `add`/`replace` assets with source hashes, old-style script additions, dependencies, target fingerprints, and persisted `numbers.json` allocations. File and directory assets are fingerprinted, with directory reports including a deterministic tree hash. External `dc2tk` check, test, and build results now include the selected executable or batch-wrapper path, size, file type, and SHA-256. `--mod-dir` allows static inventory of an authored example such as `docs/examples/calculator` without copying it under `mods/`; external commands are disabled with `--mod-dir`, so a scanned example cannot be mistaken for the selected package under `mods/`. `--run-mod-check` compiles the selected patch set, `--run-mod-test` runs the mod's offline tests, and `--run-mod-build` writes a new patched image to an explicit output path. Image builds refuse to overwrite the base disc or an existing output and are always reported as build-only. These commands require the user's local `extracted/scripts/` tree and `dc2tk`; the build flag also requires a user-owned base image. The scanner rejects source paths that escape the mod directory, contain symlinks, or point to missing files. The report fingerprints `definitions/pal` and optionally a user-provided PAL image, and records the Chronicle Two PC target plus MoonFactory package schema and Lua API versions; it does not copy the definition set or image into MoonFactory.

```powershell
python .\MoonFactory\tools\chronicle_two_script_bridge.py C:\path\to\ChronicleTwo-Script --mod my-mod --output .\my-mod-bridge-report.json
python .\MoonFactory\tools\chronicle_two_script_bridge.py C:\path\to\ChronicleTwo-Script --mod calculator --mod-dir C:\path\to\ChronicleTwo-Script\docs\examples\calculator --output .\calculator-bridge-report.json
python .\MoonFactory\tools\chronicle_two_script_bridge.py C:\path\to\DC2-Toolkit --mod my-mod --run-mod-check --run-mod-test --dc2tk C:\path\to\dc2tk.exe --disc C:\path\to\your-own-pal.iso
python .\MoonFactory\tools\chronicle_two_script_bridge.py C:\path\to\DC2-Toolkit --mod my-mod --run-mod-build --dc2tk C:\path\to\dc2tk.exe --disc C:\path\to\your-own-pal.iso --output-image .\build\my-mod.iso --output .\my-mod-build-report.json
```

`--run-mod-check` runs `dc2tk mod check extracted/scripts <mod> --disc <iso>`, `--run-mod-test` runs `dc2tk mod test extracted/scripts <mod>`, and `--run-mod-build` runs `dc2tk build extracted/scripts <iso> -o <new-image> --mod <mod>`. A successful check, test, or image build validates the offline build path only; the report continues to mark script patches and non-runtime assets as unavailable to MoonFactory's PC runtime until a separate loader and matching executable proof exist. Ten synthetic bridge tests cover report generation, path containment, asset fingerprints, external command selection, build output hashing, overwrite refusal, and skipping external commands after unsafe or failed static selection.
